# How changes are made here (cmd, the shared app and the Worker)

Every change – a fix, a new feature, a tweak – follows these rules. They grow as the rebuilds in the plan land;
when a part of the plan is done, its rule moves from "Coming" to "Rules".

## Before any new feature or change
1. Read this file and the plan (project doc `claude/plan-rebuilds-2026-11.md`).
2. If the part of the plan it touches is **done**, build it the new way (the rule is under "Rules").
3. If that part is **not done yet**, say so to the owner and either do that rebuild step first, or build the feature
   so it moves over without rework (same data shape, no new copying between cmd and the shared box, keys for texts).
   Never add more of the old way just because it's quicker.
4. Add a test for it, run all tests, then ship.
5. When a rebuild part is finished, move its line from "Coming" to "Rules" here and in the project doc `claude/rules-for-changes.md`.

## Rules
- **The repo is public.** Never commit real data, personal details (also the owner's email), tokens, keys or test files with real content. Tests use made-up data only.
- **Tests first.** Run `cd tests && node run.js -j 2` (or `node run.js <words>` for some) before pushing. A new feature or fix gets a test in `tests/cases/` that would have caught the bug. GitHub runs all tests on every push and every night; a red run is fixed before anything else.
- **Build and versions (automatic since 2026-11-11).** After changing anything in cmd run `python3 cmd/build.py`: it bundles the scripts and stamps every version from the file contents – `CACHE` in `cmd/sw.js`, every `?v=` on every page, and the shared app's `APPV`/`app.js?v=` (a counter in `cmd/home/version.json`). Never bump a version by hand. The build test (`--check`) fails if the build wasn't run.
- **Releases go through `next` (since 2026-11-11).** Push to the `next` branch, never straight to `main`. GitHub runs all tests (4 parts at once) and the Safari (WebKit) check there; only when everything is green does it move `main` to that change and tag it `release-…` – that publishes cmd and the Worker. A red run publishes nothing: fix it first. If `main` has moved, merge `main` into `next`. Undo a bad release: Actions → "undo last release" (puts the previous release back as a new change). Locally: `cd tests && node run.js -j 2` (all tests, two at a time).
- **One session at a time on the code.** Before starting, read the project doc `claude/working-on-cmd.md`. If it says another session is working, ask the owner first. Write "Working on cmd: … – started HH:MM" there when you start and "Free – last work: …" when you stop. Always merge and test on the combined code before pushing.
- **Error reports (since 2026-11-11).** cmd (`diag.js`) and the shared app send their masked error lines to `/cmd/api/errlog` (kept 21 days, owner reads only). When the owner says "check the errors", open `https://jplundberg.com/cmd/api/errlog?format=text` in the built-in browser (his sign-in) and fix what's there. Never put anything personal into an error message.
- **Safety nets (since 2026-11-11).** `/cmd/?safe` = safe mode for that tab (normal loads, no animations, "Back to normal" bar); two starts in a row that never reach the lock screen open safe mode by themselves (`dash.boot` in `diag.js`); two failed page changes in 3 days pause instant page changes on that device until the next head version (`dash.snpause` in `softnav.js`, shown in Diagnostics). A new start-up step must not delay reaching the lock screen. Test: `safe`.
- **Data changes go through `cmd/upgrades.js` (since 2026-11-11).** When the shape of saved data changes, add a numbered step at the end of `STEPS` (never edit or remove an old one); it runs once after unlocking (`data.dv`) and after restoring an older backup. No new scattered "old format" code. Test: `upgrades`.
- **Picture tests (since 2026-11-11).** `tests/cases/pictures.test.js` compares avatar drawings with `tests/pictures/*.png`. A change on purpose: `UPDATE_PICTURES=1 node run.js pictures`, look at the new pictures, then commit them. New looks or scenes get a picture case.
- **The Worker deploys itself** from `_cloudflare/` (Cloudflare Workers Builds, `_cloudflare/wrangler.jsonc`). Never ask the owner to paste code. A new binding goes into `wrangler.jsonc`; a new Durable Object class needs a new migration tag. Secrets stay in the Cloudflare dashboard – never in the repo or the chat.
- **Encryption.** Everything personal is encrypted on the device (owner: passcode vault; shared home: the shared key). The Worker only ever sees ciphertext, ids, times and version numbers. The live line (LiveRoom) carries numbers only.
- **Sync safety.** Changes from elsewhere go through `keepView()` (nothing jumps) and never overwrite a change made on this device meanwhile (`editSeq` in `lock.js`). Don't redraw a field while someone is typing in it (`typingHere()`).
- **Words.** English and Norwegian for every text. No Norwegian words in the English UI unless explained in brackets. No "undefined", "NaN" or "null" may ever reach the screen (the words test checks every page).
- **Phone first.** Check at phone width (393–440 px): no zoom, no tiny date boxes, room under the status bar, nothing hidden behind the bottom menu.
- **Who you live with is a setting** – never hard-code a name.
- **Mail:** the domain's mail is with another provider – never touch the root MX records.
- **Keep it light.** No new library or big image without need; images sized for the screen (WebP/AVIF); remove code that's no longer used. The size test (`tests/cases/size.test.js`) fails if the scripts a page loads grow past its budget – lower the budget when the app gets lighter, never raise it without a reason.
- **Icons and fonts.** cmd uses its own trimmed icon set: after using a new `bi-…` icon, run `python3 cmd/icons.py` (the build test fails otherwise). Fonts are woff2. Background images stay under ~250 kB.
- **Shared features are shared code.** Text or logic that both apps need (like `ShareCore.activity`) lives in `cmd/share-core.js`, not copied into each app. New shared kinds go into `ALLOW` with their fields and cleaning.
- **Saving in small pieces (done 2026-11-10, no switch since 2026-11-11).** On the server the vault is a small core (v: 2) plus encrypted pieces (`split()`/`join()`/`toServer()` in `cmd/lock.js`, `/cmd/api/vpiece` in the Worker). Any top-level part, widget, tool list or Health month over 2 kB becomes its own piece by itself – keep new data in its own top-level key or tool list so it lands in its own piece; don't pile it into an existing big one. Piece names stay inside the encrypted core. Backups and snapshots are whole copies. Test: `pieces`.
- **Instant page changes (done 2026-11-10, always on since 2026-11-11 – only safe mode and the pause after failures fall back).** `cmd/softnav.js` (last in head) swaps the page without a reload and runs the page bundle and `tail.js` again; what they set up on things that stay (listeners on window/document/html/body, intervals, timers, observers, WebSockets, `<html>` classes, additions to head objects, `Vault.onUnlock`) is undone when you leave – who made it is read from the call stack. So: a page/tail module may run many times per session – keep lasting state in a store (vault, localStorage, the shared box), never only in module variables; head modules (`scripts.json` head) run once and must use event delegation for page elements. Test: `softnav` (13 page changes, nothing doubled, Back, Settings, lock).
- **Shared home in one place (done 2026-11-10, always on since 2026-11-11).** Shared things are read straight from the shared box – no copying into the owner's vault: shopping list, chores + rooms + ticks, dinners + votes, notes (`DLISTS` in `cmd/share.js` + `Features.direct()`; a part the box keeps only for a while gets a `win`) and shared calendar events (`EV` in share.js: the calendar copy is kept equal to the box; `vault:in` from lock.js puts the box's version back over another device's older copy). Edits become changes for the box (`dash.share.ops.*`) and are sent with the next sync; the vault keeps a backup copy. **A new shared list goes into `DLISTS`**, never into `collect()`/`applyAll()`. Money stays worked out from the finances; pantry, recipes and plants are published one way. There are no off switches any more (step 7, 2026-11-11): the box wins – a device's own copy only adds what the box has never seen, it never removes or overwrites what's there, and kinds read from the box are never copied into the vault by `applyAll()`. Tests: `shop-direct`, `chores-direct`, `dinner-direct`, `events-direct`.
- **The two of you (Phase E, 2026-11-11).** Features for both of you live once in `cmd/together.js`, loaded by cmd (tail) and the shared app; each app plugs in an adapter (`Together.use`). Their records are kinds either of you writes: add the kind to `ALLOW` (share-core.js) and to `BOTH` (share.js – cmd's outbox `dash.share.tg`, never deleted just because a copy lacks it). A reminder for later goes through the Worker (`notify.at` → `push:nudge:*`, sent by the live room's alarm). Tests: `together`, `avatar-day`.
- **Living scenes (done 2026-11-11).** Your avatar on each page picture is alive (`cmd/scene-<page>.js` on top of the still picture from `scenes.js`; engine `scene-kit.js` (`Live`), rig `avatar-rig.js`, shared props and everyday actions `scene-common.js`). Every animated thing is its own component; actions only use components (walk, reach, take, drink, wave…) – no one-off drawing inside an action and no CSS animations of you in `scenes.js` (still pictures stay still: reduced motion, "Still pictures", safe mode). Every action passes the staging checklist (`claude/plan-living-scenes-2026-11.md`: stand, face, grip, prop direction, front/behind, look, real size – a suitcase is waist high, weight and order, everything back) and is looked at frame by frame before shipping. A new look or view gets a picture case; anything that goes to the mouth gets a `scene-staging` case. Tests: `scene-pages`, `scene-finance`, `scene-people-travel`, `scene-staging`, `scene-softnav`, `views`, `pictures`.
- **Ask before** anything that can't be undone (deleting data, changing DNS, scheduled tasks).

## Coming (from the plan – becomes a rule when that part is done)
- **Translations:** every text has a fixed name (key); never match on the English sentence.
- **Reminders:** sent by the server (LiveRoom alarms), not planned by a device.
- **Offline:** every edit goes through the offline queue.
- **Lighter app:** each page loads only its own code.

The full plan: project doc `claude/plan-rebuilds-2026-11.md`.
