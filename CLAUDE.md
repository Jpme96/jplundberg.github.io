# How changes are made here (cmd, the shared app and the Worker)

Every change – a fix, a new feature, a tweak – follows these rules. They grow as the rebuilds in the plan land;
when a part of the plan is done, its rule moves from "Coming" to "Rules".

## Before any new feature or change
1. Read this file and the plan (project doc `claude/plan-rebuilds-2026-11.md` – Phase F there is the 2.5D avatar and scenes).
2. If the part of the plan it touches is **done**, build it the new way (the rule is under "Rules").
3. If that part is **not done yet**, say so to the owner and either do that rebuild step first, or build the feature
   so it moves over without rework (same data shape, no new copying between cmd and the shared box, keys for texts).
   Never add more of the old way just because it's quicker.
4. Add a test for it, run all tests, then ship.
5. When a rebuild part is finished, move its line from "Coming" to "Rules" here and in the project doc `claude/rules-for-changes.md`.

## Rules
- **The repo is public.** Never commit real data, personal details (also the owner's email), tokens, keys or test files with real content. Tests use made-up data only.
- **Tests first.** Run `cd tests && node run.js -j 2` (or `node run.js <words>` for some) before pushing. A new feature or fix gets a test in `tests/cases/` that would have caught the bug. GitHub runs all tests on every push and every night; a red run is fixed before anything else.
- **Build and versions (automatic since 2026-11-11).** After changing anything in cmd run `python3 cmd/build.py`: it bundles the scripts and stamps every version from the file contents – `CACHE` in `cmd/sw.js`, every `?v=` on every page, and the shared app's `APPV`/`app.js?v=` (a counter in `cmd/home/version.json`). Never bump a version by hand. The build test (`--check`) fails if the build wasn't run.
- **Releases go through `next` (since 2026-11-11).** Push to the `next` branch, never straight to `main`. GitHub runs all tests (4 parts at once) and the Safari (WebKit) check there; only when everything is green does it move `main` to that change and tag it `release-…` – that publishes cmd and the Worker. A red run publishes nothing: fix it first. If `main` has moved, merge `main` into `next`. Undo a bad release: Actions → "undo last release" (puts the previous release back as a new change). Locally: `cd tests && node run.js -j 2` (all tests, two at a time).
- **One session at a time on the code.** Before starting, read the project doc `claude/working-on-cmd.md`. If it says another session is working, ask the owner first. Write "Working on cmd: … – started HH:MM" there when you start and "Free – last work: …" when you stop. Always merge and test on the combined code before pushing.
- **Error reports (since 2026-11-11).** cmd (`diag.js`) and the shared app send their masked error lines to `/cmd/api/errlog` (kept 21 days, owner reads only). When the owner says "check the errors", open `https://jplundberg.com/cmd/api/errlog?format=text` in the built-in browser (his sign-in) and fix what's there. Never put anything personal into an error message.
- **Safety nets (since 2026-11-11).** `/cmd/?safe` = safe mode for that tab (normal loads, no animations, "Back to normal" bar); two starts in a row that never reach the lock screen open safe mode by themselves (`dash.boot` in `diag.js`); two failed page changes in 3 days pause instant page changes on that device until the next head version (`dash.snpause` in `softnav.js`, shown in Diagnostics). A new start-up step must not delay reaching the lock screen. Test: `safe`.
- **Data changes go through `cmd/upgrades.js` (since 2026-11-11).** When the shape of saved data changes, add a numbered step at the end of `STEPS` (never edit or remove an old one); it runs once after unlocking (`data.dv`) and after restoring an older backup. No new scattered "old format" code. Test: `upgrades`.
- **Picture tests (since 2026-11-11).** `tests/cases/pictures.test.js` compares avatar drawings with `tests/pictures/*.png`. A change on purpose: `UPDATE_PICTURES=1 node run.js pictures`, look at the new pictures, then commit them. New looks or scenes get a picture case.
- **The Worker deploys itself** from `_cloudflare/` (Cloudflare Workers Builds, `_cloudflare/wrangler.jsonc`). Never ask the owner to paste code. A new binding goes into `wrangler.jsonc`; a new Durable Object class needs a new migration tag. Secrets stay in the Cloudflare dashboard – never in the repo or the chat.
- **Encryption.** Everything personal is encrypted on the device (owner: passcode vault; shared home: the shared key). The Worker only ever sees ciphertext, ids, times and version numbers. The live line (LiveRoom) carries numbers only.
- **Sync safety.** Changes from elsewhere go through `keepView()` (nothing jumps) and never overwrite a change made on this device meanwhile (`editSeq` in `lock.js`). Don't redraw a field while someone is typing in it (`typingHere()`).
- **Words.** English and Norwegian for every text. No Norwegian words in the English UI unless explained in brackets. No "undefined", "NaN" or "null" may ever reach the screen (the words test checks every page).
- **Phone first.** Check at phone width (393–440 px): no zoom, no tiny date boxes, room under the status bar, nothing hidden behind the bottom menu.
- **Who you live with is a setting** – never hard-code a name.
- **Mail:** the domain's mail is with another provider – never touch the root MX records.
- **Keep it light.** No new library or big image without need; images sized for the screen (WebP/AVIF); remove code that's no longer used. The size test (`tests/cases/size.test.js`) fails if the scripts a page loads grow past its budget – lower the budget when the app gets lighter, never raise it without a reason.
- **Icons and fonts.** cmd uses its own trimmed icon set: after using a new `bi-…` icon, run `python3 cmd/icons.py` (the build test fails otherwise). Fonts are woff2. Background images stay under ~250 kB.
- **Shared features are shared code.** Text or logic that both apps need (like `ShareCore.activity`) lives in `cmd/share-core.js`, not copied into each app. New shared kinds go into `ALLOW` with their fields and cleaning.
- **Saving in small pieces (done 2026-11-10, no switch since 2026-11-11).** On the server the vault is a small core (v: 2) plus encrypted pieces (`split()`/`join()`/`toServer()` in `cmd/lock.js`, `/cmd/api/vpiece` in the Worker). Any top-level part, widget, tool list or Health month over 2 kB becomes its own piece by itself – keep new data in its own top-level key or tool list so it lands in its own piece; don't pile it into an existing big one. Piece names stay inside the encrypted core. Backups and snapshots are whole copies. Test: `pieces`.
- **Instant page changes (done 2026-11-10, always on since 2026-11-11 – only safe mode and the pause after failures fall back).** `cmd/softnav.js` (last in head) swaps the page without a reload and runs the page bundle and `tail.js` again; what they set up on things that stay (listeners on window/document/html/body, intervals, timers, observers, WebSockets, `<html>` classes, additions to head objects, `Vault.onUnlock`) is undone when you leave – who made it is read from the call stack. So: a page/tail module may run many times per session – keep lasting state in a store (vault, localStorage, the shared box), never only in module variables; head modules (`scripts.json` head) run once and must use event delegation for page elements. Test: `softnav` (13 page changes, nothing doubled, Back, Settings, lock).
- **Shared home in one place (done 2026-11-10, always on since 2026-11-11).** Shared things are read straight from the shared box – no copying into the owner's vault: shopping list, chores + rooms + ticks, dinners + votes, notes (`DLISTS` in `cmd/share.js` + `Features.direct()`; a part the box keeps only for a while gets a `win`) and shared calendar events (`EV` in share.js: the calendar copy is kept equal to the box; `vault:in` from lock.js puts the box's version back over another device's older copy). Edits become changes for the box (`dash.share.ops.*`) and are sent with the next sync; the vault keeps a backup copy. **A new shared list goes into `DLISTS`**, never into `collect()`/`applyAll()`. Money stays worked out from the finances; pantry, recipes and plants are published one way. There are no off switches any more (step 7, 2026-11-11): the box wins – a device's own copy only adds what the box has never seen, it never removes or overwrites what's there, and kinds read from the box are never copied into the vault by `applyAll()`. Tests: `shop-direct`, `chores-direct`, `dinner-direct`, `events-direct`.
- **The two of you (Phase E, 2026-11-11).** Features for both of you live once in `cmd/together.js`, loaded by cmd (tail) and the shared app; each app plugs in an adapter (`Together.use`). Their records are kinds either of you writes: add the kind to `ALLOW` (share-core.js) and to `BOTH` (share.js – cmd's outbox `dash.share.tg`, never deleted just because a copy lacks it). A reminder for later goes through the Worker (`notify.at` → `push:nudge:*`, sent by the live room's alarm). Tests: `together`, `avatar-day`.
- **Offline (done 2026-11-11).** No edit needs the network: the vault saves on the device first; shared lists wait as changes (`dash.share.ops.*` in cmd, `home.queue` in the shared app); kinds for the two of you wait in cmd's outbox (`dash.share.tg`); every other write goes through `ShareCore.send(path, opt, key)` (the queue `dash.outq`, resent when you're back online – only network failures queue). Never a bare `fetch`/`api` for a write. The "N changes waiting" chip shows what's waiting. Tests: `outq`, `waiting`.
- **2.5D avatar and scenes (F1–F2 done 2026-11-12; F4 removed the old engine).** You are drawn by one body, `cmd/avatar-25d.js` (`Fig25`: `draw`/`group`/`hand`, a pool per person, `HOLDS`, `BUILD`); `Avatar.figure()` puts it in the moment's frame and `Avatar.act25` plays small moves. Each page picture is a scene on `cmd/scene25.js` (`Scene25.run(svg, {len, back, render, hits, pick, data})`: the still layer is drawn once, the front layer each frame; it rests at 30 fps, sleeps off screen, and still pictures (reduced motion, "Still pictures", safe mode) draw the last frame), one file per page `cmd/scene-<page>.js`, the couple in `scene-couple.js`, the Journey and "See it move" on the same engine. No flat drawing, no CSS animation of you. Every scene and every action meets the seven build criteria before it ships:
  1. **Customisation is handled properly on the characters.** Every kept choice is drawn in every view; clothes stay on the body; hair, hats and beards never stick out past the head.
  2. **Look and character work together, scene by scene.** Each scene is checked with the look sweep (varied looks, wheelchair and crutches included); props and clothes don't fight.
  3. **Actions are proper behaviour.** They pass the staging checklist (11 points, props laid properly), follow real-life order, and fit the data.
  4. **More actions.** At least four per page, idle moves, tap interactions, time and season versions, never twice in a row.
  5. **It runs smoothly.** 60 fps and under 4 ms a frame; endings flow into the rest; no teleports (`scene25-pages` checks every frame's hands).
  6. **Good movement, no visual bugs.** Look first, then fix: contact sheets and big frames, the problem list written down and fixed, then shown to JP with that list.
  7. **Props follow the action and fit the scene.** Every action has the props it needs; a prop matches the scene's style, palette, light, size and perspective, lives somewhere believable and goes back there.
  Page observers never hear a scene's frames (diag.js skips nodes marked `__sc` by `el()`); still scenery goes in `back`. Tests: `fig25`, `scene25`, `scene25-pages`, `scene-acts`, `scene-observers`, `scene-couple`, `scene-softnav`, `scene-sizes`, `scene-speed`, `avatar-moves`, `pictures`.
  **The body's look (2026-11-13, after JP's reference picture):** a lean, about 7.3-head figure. Each build in `BUILD` has its own front widths (`sx`, `ch`, `wv`, `hv`, `ar`); the legs are half the height through the leg factor `lf` (the skeleton numbers stay: shoulders 88, hips 140, legs 38 + 36); the head is scaled round the chin (`HSX` × `HSC`, a little bigger when he is drawn small). The trunk's levels (`LV`: height, half the width from the front, half the depth, how far forward) keep the chest about two thirds as deep as it is wide – from the side its front is a soft line and the back a slight S, never a point at the chest (JP). A limb is one flowing shape: inside `whole(col, z, fn, rim)` the `taper()` calls only record their pieces. Every part is filled with `grad(colour)` – a gradient of its own colour with the plain colour as the fallback (`grad(c, 1)` = a dome: shoulders, hands, kneecaps); never fill a body part with a flat colour, and a new colour needs nothing more than `grad()`. Big enough to see (`k > .85`: `CEL` on the body, `DET` on the face) he gets the detailed face and the light and dark shapes; small (the page scenes) the same parts are drawn bolder and fewer – anything new and fine goes behind those two switches so a scene frame stays cheap. Everything inside the `head` group is drawn round the head's middle (`hc` = 0,0; `HC` is the real place, `PH()` a body point relative to it) and the whole group is kept from the last frame while the turn, size, look and blink are the same – so nothing inside it may depend on the bob or the breath. A new option (hair, beard, hat, top) is checked in front, ¾, side and back with the sheet tools before it ships, also under a hat and on every build.
  **Talking, brows, aids (F6, 2026-11-13):** `pose.mouth` = `'a'`, `'o'`, `'e'` or `'m'` (the closed mouth of his mood) – `Fig25.viseme(t)` gives the shape for a moment of speech, so a scene sets `pose.mouth = Fig25.viseme(t)` while he says something; `pose.brow` = `'up'`, `'down'` or `'sad'` (the moods `wow` and `shy` set theirs). Both are part of the head's key, so nothing else is needed. On crutches a hand with a pose of its own lets go of its crutch, which stays standing by his side – never draw a crutch to a raised hand. In the wheelchair he must still be seen: where furniture stands in front of him (the Work desk) seat him higher behind it. The pets (`pet()`) follow the body's look: `grad()` fills, a dome for the head, the finest bits only when drawn big. A new action is looked at with the wheelchair and with crutches (contact sheets) before it ships.
  **Frames (2026-11-12 night):** inside `render` a frame is built off the page from pooled elements (`Scene25.el/add` and Fig25's pool keep their attributes in `_a` only) and `patch()` writes just the differences into the live picture – so in `render` never read an element's attributes back, never set one with `setAttribute` (pass it to `el()`/`add()`), and mark cached art made with `innerHTML` `__static`. Measured with a 4× slower CPU in `scene-speed` (every page under 4 ms). **Taps (F3):** a 6th item in `hits` (or `data-scact` on a `data-scgo` thing) names the action a tap plays – the card still opens. **Seasons (F3):** `spec.season = { x, y, s }` (the foot of the prop, a little behind his walking line; `act: false` = the prop only) gives the tree in December and the pumpkin from 20 October, and with `out: 1` (an outdoor page) a snowman in January and February; `window.__season` forces one for previews and tests. A scene that pans (the Journey) draws the prop with its own scenery through `Scene25.seasonProp(par, x, y, s)`. An everyday action that walks has `walk: 1`, steps from the distance (`PHR`) and `done(st)` for what stays.
- **Texts by name (Phase D 24, 2026-11-11).** A new text gets a fixed name: in HTML `data-t="ui.some-words"` on the element whose own text it is (`data-t-aria-label` / `-placeholder` / `-title` for attributes), in scripts `I18N.k('ui.some-words', 'English', {n: 3})` (`{n}` is filled in); its `[English, Norwegian]` goes into `cmd/words/ui.nb.js` (loaded only in Norwegian, in `dist/nb.js`). Never add to the old sentence list in `i18n-nb.js` – it only shrinks: `python3 cmd/i18n-keys.py ui <files>` names what it can (`--wrap`: also the pieces of text between tags, each in its own `<span data-t>`; `--args`: labels passed to helpers become `I18N.k`, never inside arrays – those may be seed data that gets saved; `--opts`: the labels of choices `[value, 'Label']`, which are only shown – never in head modules, they run before the words load; `--props`: a card's set-up words `title` / `empty` / `addLabel: 'English'` (kit.js shows them); a count or a time inside a sentence: `I18N.k('ui.n-people', '{n} people', { n: 4 })` with `{n} personer` added to `words/ui.nb.js` by hand), `python3 cmd/i18n-keys.py ui --prune` takes named sentences out. Not in files the shared app loads (it has no `I18N`). Change the English next to a name → change it in the words file too. A name used through a short alias (`var K = I18N.k; K('ui.x', …)`) counts as used – `text-keys` checks that every name in code has its words (2026-11-13: a prune had taken out 11 such names). Tests: `text-keys`, `norwegian` (per page: how much is still matched on the sentence – lower those numbers as pages move over).
- **A page's own code loads only on that page (Phase D 25 – House 2026-11-11; Papers, Work, Habits water, Goals, Wishlist, House chores 2026-11-12; the home-life split – home-life, people-plus, food-plus, money-plus, fin-tools, home-shared, life-pages – 2026-11-12 night, done).** A module for one page is split by `node cmd/split-page.js <file.js> <key> [API names other pages use]`: `<file>.js` stays in tail.js as the *everywhere part* (the hooks other pages use – At a glance `BriefExtra`, ⌘K `CommandExtra`, `SearchExtra`, calendar `EventsExtra`, `HF.uses` – the data they need and the window API's data methods; it publishes `window.__core[key]`); `<file>.page.js` is the *page part* (cards, sheets, its listeners), listed under `late` for its page in scripts.json and run after tail.js (`late.js`). The everywhere part reaches page things only through `__ui()` (empty on other pages: a command there goes to the page instead). New code for one page goes into its `.page.js`; something other pages need goes into the everywhere part. The hook lists are head objects (features.js), so they're refilled on each page, never doubled. What must run on every page stays in the everywhere part: Settings rows and their handlers (the tool keeps `.st-page`, `st:page`, `st-row`, `[data-…cfg]` and any handler for a `data-…` button the everywhere part draws), data jobs at unlock or sync (clean-ups, flags, a refresh event other pages listen to) and every API method another file calls – also through an alias like `var S = window.Shared`. Read the page part for those before shipping. A page part used by several pages is listed under `late` for each of them (home-life.page.js: House, People, Food, Work). After the tool, check by hand: a guard like `if (!HL) return;` must come after the line that takes `HL` from `__c`; every `__ui().x(…)` in the everywhere part is guarded (`if (__ui().x) … else location.href = …`); data jobs (`syncShop`, the rate watch, a clean-up at unlock), things on every page's top bar (the Top 3 ring, the eye) and sheets opened from At a glance or ⌘K stay in the everywhere part. Test: `home-split`. **CSS per page (2026-11-12):** rules only one page uses live in `cmd/<page>/page.css`, linked right after styles.css on that page; `python3 cmd/split-css.py` (`--write`) moves every rule whose classes only that page's own scripts and HTML use (softnav puts a page's stylesheet in the same place on an instant change). A new style for one page goes into its `page.css`. Tests: `house-split`, `page-split`, `css-split`, `size` (a budget per page – lower it, never raise it).
- **Colours as tokens (done 2026-11-11).** Light and dark come from one set of named colours: the `:root` block (dark) and `:root[data-theme="light"]` right after it in `styles.css` (and modern.css's own pair) are the only places that know the theme. Status colours by name – `var(--ok)`, `--warn`, `--danger`, `--orange`, `--blue`, `--gold`, `--pink`, `--violet`, `--slate` (with `-rgb` for see-through: `rgba(var(--ok-rgb), .2)`), never their hex. Something that should look different in light = a token in both blocks (or a light-only token used as `var(--x, dark value)`), never a `[data-theme="light"] .thing` rule. Test: `colors`.
- **Reminders are sealed on the device (F-R, 2026-11-12).** Each device seals a reminder's title and text with its own key (`cmd/push-key.js`, `PushKey.sealItems`, the key is kept in IndexedDB and never leaves the device) before the list goes to `/cmd/api/push`; the Worker keeps only the time, an id, the page and the ciphertext (it drops any readable text) and the live room's alarm sends it on the minute; both service workers open it (`importScripts('/cmd/push-key.js')`) and show a plain "Reminder" if they can't. Never upload readable reminder text. Pushes to the other one (nudges `push:nudge:*`, "N added milk", chat lines) are sealed with a key made from the shared key (`PushKey.keepShared/sealShared`, HKDF) – `ShareCore.send('push', …)` seals the title and text before anything is sent or queued, the Worker keeps and forwards only `c` (it drops readable text) and the phones open it with `PushKey.text`. Never send a push to the other one past `ShareCore.send`. Tests: `reminders-server`, `push-shared`.
- **Ask before** anything that can't be undone (deleting data, changing DNS, scheduled tasks).
